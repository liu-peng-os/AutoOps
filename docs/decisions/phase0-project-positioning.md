# 阶段0决策：项目定位

> 决策时间：2026-04-23
> 决策状态：已确认
> 相关文档：`docs/roadmap.md`

---

## 背景

AutoOps 项目是从某个开源运维平台 fork 而来。fork 之后面临一个核心问题：

**这个项目未来是"持续跟进上游代码"，还是"独立演进自己的平台"？**

这个问题决定了后续所有技术选型、架构改造、模块边界的方向。

---

## 决策

**AutoOps 后续按独立运维平台演进，不再以低成本持续兼容 upstream 为首要目标。**

上游项目仍可作为参考，但本项目优先追求：
- 长期可维护
- 模块边界清晰
- 数据库演进可控
- 外部系统可替换

---

## 理由

### 为什么不持续跟进上游

1. **上游代码的技术债已经影响二开效率**
   - 数据库 schema 演进依赖 `AutoMigrate`，无法 review 和回滚
   - 外部系统调用散落在业务代码中，难以替换
   - 模块边界不清晰，改一个功能要动多个地方

2. **业务需求和上游方向不完全一致**
   - 上游侧重某些特定场景，我们需要的能力不在上游优先级里
   - 我们需要接入飞书多维表格、dnsmgr 等外部系统，上游不会做这些

3. **持续兼容的成本高于独立演进**
   - 每次上游更新都要评估兼容性，cherry-pick 成本高
   - 为了兼容上游，很多改造不敢做，技术债越积越多

### 为什么选择独立演进

1. **我们有明确的业务场景和用户**
   - 核心用户是内部运维团队，需求明确
   - 不需要追求"通用性"，可以针对实际场景优化

2. **独立演进可以做更彻底的改造**
   - 可以切换到 PostgreSQL，更适合平台型系统
   - 可以引入 migration 工具，让 schema 演进可追溯
   - 可以重新划分模块边界，降低维护成本

3. **上游代码仍然有参考价值**
   - 产品理念和功能方向可以继续参考
   - 某些实现细节可以借鉴
   - 但不需要强制保持代码级兼容

---

## 否决的方案

### 方案A：完全重写

**为什么否决**：
- 重写成本太高，短期内无法交付
- 现有代码里有很多已经验证过的业务逻辑，重写会丢失这些积累
- 团队对现有代码库有一定理解，完全重写会浪费这些经验

### 方案B：持续跟进上游

**为什么否决**：
- 上游更新频率不确定，可能长期不更新，也可能突然大改
- 每次合并上游代码都要解决冲突，成本高
- 为了兼容上游，很多改造不敢做，技术债无法清理

### 方案C：保持现状，只做小修小补

**为什么否决**：
- 技术债会越积越多，最终无法维护
- 数据库 schema 演进不可控，出问题难以回滚
- 外部系统耦合在业务代码里，替换成本高

---

## 影响

这个决策带来的影响：

1. **技术选型自由度更高**
   - 可以切换到 PostgreSQL
   - 可以引入 goose 等 migration 工具
   - 可以重新设计模块边界

2. **需要自己维护所有代码**
   - 上游的 bug 修复不会自动同步过来
   - 需要自己做安全更新和依赖升级

3. **文档和交接成本增加**
   - 需要记录所有决策和改造过程
   - 新人接手时需要理解我们的架构，而不是上游的架构

---

## 约束条件

这个决策基于以下约束：

1. **团队规模**：小团队，无法同时维护多个分支
2. **业务需求**：需要快速响应内部需求，不能等上游更新
3. **技术债**：现有代码的技术债已经影响开发效率
4. **外部依赖**：需要接入多个外部系统（飞书、dnsmgr 等）

如果这些约束条件发生变化（比如团队扩大、上游方向和我们一致），可以重新评估这个决策。
