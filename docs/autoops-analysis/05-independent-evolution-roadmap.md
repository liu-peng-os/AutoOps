# AutoOps 二次开发独立演进版技术选型与分阶段迁移路线

> 版本：1.0  
> 日期：2026-04-23  
> 定位：面向“基于原项目理念重构自己的平台”，而不是以持续兼容 upstream 代码为首要目标。

---

## 一、目标定义

当前 fork 后的新项目，目标不是长期追随原项目技术实现，而是：

1. 保留原项目中已经验证过的功能方向与产品理念。
2. 允许在架构、数据模型、工程体系上做较大改造。
3. 后续对原项目更新以“参考借鉴”为主，而不是要求低成本 cherry-pick。
4. 为未来 1-3 年持续二开、扩展模块、提高稳定性与维护效率做准备。

在这个目标下，技术选型的第一原则不再是“和原项目保持兼容”，而是：

- 长期可维护
- 模块边界清晰
- 数据演进可控
- 前后端开发效率高
- 对异步任务、审计、配置、资源关系这类平台型场景友好

同时，新项目还需要坚持一个额外原则：

- 优先建设通用能力，不把平台做成和某一家外部工具深度绑定的定制系统
- 所有外部系统都应视为“可替换依赖”，而不是核心模型本身
- 后续如果切换到其他协同平台、DNS 平台、监控平台，应尽量只替换接入层，而不是重做业务层和数据库主模型

## 二、最终推荐技术栈

### 1. 后端

- 语言：`Go 1.24+`
- Web 框架：`Gin`
- 鉴权：`golang-jwt/jwt`
- ORM：`GORM`
- 数据库迁移：`golang-migrate` 或 `goose`
- 配置管理：`Viper` 或保持轻量 yaml/env 方案
- 日志：优先统一结构化日志，保留 `logrus` 或逐步迁移到 `slog`

**建议原则**：

- 保留 `Gin`，不为了“更现代”而切到新框架。
- 保留 `GORM` 处理日常 CRUD，但复杂查询、统计查询、批量更新可使用手写 SQL。
- 停止把数据库结构演进建立在 `AutoMigrate` 之上，改为显式 migration。

### 2. 数据层

- 主数据库：`PostgreSQL 16`
- 缓存：`Redis`
- 异步任务：`asynq`

开发环境当前已确认的 PostgreSQL 连接信息：

- Host：`52.82.70.176`
- Port：`5432`
- Database：`mydb`
- Username：`admin`
- Password：`1qaz@WSXQWER`

**为什么选 PostgreSQL**：

- 更适合平台型系统里的 JSON / 配置 / 资源关联查询。
- 对后续审计、任务、资源标签、策略规则等数据形态更友好。
- 长期 schema 演进与复杂查询能力通常优于当前项目对 MySQL 的依赖方式。

**为什么选 asynq**：

- 它不是替代 Redis，而是“基于 Redis 的现成任务队列框架”。
- 比当前手工 Redis 队列方式更容易拿到重试、延迟执行、失败管理、并发控制、任务状态等能力。

### 3. 前端

- 框架：`Vue 3`
- 构建工具：`Vite`
- 语言：`TypeScript`
- 状态管理：`Pinia`
- UI 组件：`Element Plus`
- 图表：`ECharts`
- 终端：`xterm`
- 编辑器：`Monaco`

**建议原则**：

- 不切换到 React / Next，避免无意义重学与生态迁移。
- 保留 Vue 体系，但把老旧工程壳升级为 `Vite + TS + Pinia`。
- 保留 `Element Plus`，因为它对后台平台场景依然高效。

### 4. 交付与部署

- 开发与联调：`Docker Compose`
- 生产部署：前期可继续容器化部署，后续视规模接入 `Kubernetes`
- API 文档：保留 `Swagger/OpenAPI`

## 三、核心架构建议

如果要真正独立演进，最重要的不是先换库，而是先重新划分边界。

建议把系统拆成三层：

### 1. 核心域

承载平台长期稳定的基础能力：

- 用户 / 角色 / 权限 / 组织
- 审计日志
- 资源主数据
- 任务与调度
- 配置与密钥元数据

### 2. 业务能力域

在核心域之上扩展业务能力：

- CMDB
- K8s 管理
- 部署发布
- 监控与告警
- 配置中心

### 3. 集成适配层

负责对接外部系统，不把外部平台耦合进核心模型：

- Jenkins
- Prometheus
- 云厂商 SDK
- SSH / SFTP
- 通知渠道

**设计原则**：

- 核心域优先稳定。
- 业务能力域依赖核心域，但不要直接共享杂乱表结构。
- 集成适配层只能通过明确接口进入业务层，避免到处散落外部调用逻辑。

### 4. 可插拔集成原则

为了保证后续能迁移到其他公司或替换第三方工具，新增模块和外部依赖都应遵守以下约束：

- 核心域不直接依赖任何具体外部产品。
- 外部平台统一通过 adapter / provider 方式接入，不把第三方 SDK 调用散落在业务代码中。
- 平台内部数据模型只保存通用业务字段、外部对象映射关系、同步状态和审计信息。
- 不把任何第三方系统的专有字段直接铺满核心业务主表。
- 模块设计默认按“核心模型 + 集成适配器 + 同步任务/调用服务”拆分。
- 替换外部系统时，目标应是主要调整适配层，而不是推翻页面、业务服务和数据库主结构。

## 四、与原项目相比的关键改造决策

### 决策 1：保留 Go + Gin，不重写后端语言

这是“高收益低风险”的选择。

- 现有团队理解成本低。
- 可以继续参考原项目的接口设计与业务组织方式。
- 真正的问题不在语言，而在模块边界、数据演进和任务体系。

### 决策 2：数据库切到 PostgreSQL

这是“中高成本但长期收益明显”的改造。

- 既然目标是独立演进，就不必再被原项目的 MySQL 偏好绑住。
- 未来资源标签、策略、任务参数、扩展配置等更适合在 PG 上演化。

### 决策 3：继续用 GORM，但放弃 AutoMigrate 作为主方案

建议模式：

- GORM：负责业务 CRUD
- migration 工具：负责建表、改表、索引、数据迁移

这样数据库演进会更透明、可 review、可回滚。

### 决策 4：任务系统从“手工 Redis 队列”升级到 asynq

目标不是炫技，而是减少手工维护成本。

适合迁移到 asynq 的任务：

- 批量脚本执行
- 主机信息同步
- 云资源同步
- 定时巡检
- 延迟执行任务
- 部署后台任务

不必迁移到 asynq 的能力：

- WebSocket 终端
- 实时日志流
- 前端通知推送

### 决策 5：前端升级到 Vite + TypeScript + Pinia

这部分是“工程层升级”。

- `Vite` 提高开发体验
- `TypeScript` 提高长期可维护性
- `Pinia` 替代旧式 `Vuex`

### 决策 6：新增能力优先按“统一入口 + 可替换接入”设计

当前阶段不计划删除旧功能，但会新增三类能力：

- 新增一级菜单 `域名管理`
- 新增一级菜单 `运营工单`
- 在 `资产管理` 下新增 `站点管理`

这些能力的设计原则不是“把外部工具硬编码进平台”，而是：

- `域名管理` 短期作为 `dnsmgr` 的统一接入口，后续如有需要再逐步增强平台内的汇总与联动能力
- `运营工单` 长期以飞书多维表格为主数据源，AutoOps 负责查询、编辑、回写和审计
- `站点管理` 长期以飞书多维表格为主数据源，AutoOps 负责查询、编辑、回写和审计

这三类能力都应在架构上保留替换空间，避免未来因第三方工具变化而推翻平台内部模型

## 五、推荐目录与工程组织

### 后端建议结构

```text
server/
  cmd/
    api/
  internal/
    core/          # 用户、权限、审计、资源、任务等核心域
    cmdb/
    k8s/
    deploy/
    monitor/
    configcenter/
    integration/   # Jenkins、Prometheus、Cloud、SSH 等适配器
  pkg/
    db/
    cache/
    auth/
    log/
    config/
  migrations/
```

### 前端建议结构

```text
web/
  src/
    app/
    router/
    stores/
    api/
    modules/
      cmdb/
      k8s/
      deploy/
      monitor/
      system/
    components/
    utils/
```

这样做的目的，是让“模块”成为真正的组织单位，而不是只按 controller/service/dao 平铺。

### 4. 阶段 1：通用底座搭建

目标：先把“以后所有开发都要依赖的公共设施”搭起来。

当前已落地：

- 外部系统接入目录 API 骨架
- 新增模块前端路由占位页
- 左侧菜单的阶段性引导入口
- 认证失败日志泄密问题修正

计划落地内容：

- 新仓库主分支结构
- Go 服务骨架
- PostgreSQL + Redis 本地开发环境
- GORM 接入
- migration 机制接入
- JWT 鉴权替换为 `golang-jwt/jwt`
- 基础日志、配置、错误码、审计框架
- 外部系统适配层骨架
- 同步任务 / 回写任务基础框架
- 前端 `Vue 3 + Vite + TS + Pinia + Element Plus` 骨架

进入阶段 2 的标志：

- 本地开发环境稳定可复用
- 前后端基础骨架可持续开发
- 鉴权、配置、日志、migration 方案正式定稿
- 外部接入层具备承载首批接入型模块的能力

### 5. 阶段 2：接入型能力闭环

目标：优先把当前最明确的新增能力做出可用闭环，不急着把所有业务模块边界一次定死。

优先落地：

- `域名管理`：先完成 `dnsmgr` 接入入口
- `运营工单`：先完成飞书多维表格同步、展示、基础编辑回写闭环
- `站点管理`：先完成飞书多维表格同步、展示、基础编辑回写闭环

原因：

- 这些方向已经明确，而且不需要先把所有旧模块推翻重做。
- 通过先做接入型闭环，可以反向验证适配层、同步机制和通用模型设计是否合理。

进入阶段 3 的标志：

- 至少形成 1-2 个稳定可用的新能力闭环
- 同步、回写、审计、错误处理机制经过实际验证
- 外部系统接入抽象被证明可复用

### 6. 阶段 3：模块化增强

目标：按实际优先级逐步增强业务模块，并在进入每个模块开发时再细化该模块边界。

建议方式：

- 不提前把所有模块未来形态一次定死
- 哪个模块要开始做，就先补该模块的边界、字段、交互和同步策略
- 旧模块先维持可用，新模块按明确需求逐步增强

可进入的方向包括：

- CMDB 资产管理增强
- 任务系统增强
- K8s 管理增强
- 部署发布增强
- 监控告警增强
- 更多外部系统接入

原则：

- 先保留最小闭环，不追求一次迁完所有细枝末节。
- 优先迁“高频使用功能”，低频功能可以延后。
- 模块边界在进入该模块开发时单独确认并回填文档。

### 7. 阶段 4：治理与优化

目标：在已有模块和接入能力可用的基础上，完善平台治理能力。

计划落地内容：

- 审计完善
- 安全脱敏与密钥治理
- 可观测性
- 限流与并发控制
- 任务重试策略优化
- 适配器治理与替换能力验证

### 8. 文档回填规则

为了让后续接手的人能快速判断背景和进度，这份文档后续应按以下方式回填：

- 每次阶段状态变化，只更新“当前状态”和“阶段状态总览”
- 每次新增或撤销结论，优先回填到对应阶段的“已确认 / 待收口”部分

- 每个阶段完成时，补一条“阶段结束标志已满足”的说明

## 八、优先级建议

### 高优先级

- `jwt-go -> golang-jwt/jwt`
- 停止依赖 AutoMigrate
- 引入 migration 机制
- 前端升级到 Vite
- 统一敏感信息治理
- 新任务系统选型落地（建议 asynq）

### 中优先级

- PostgreSQL 16 迁移
- Pinia 全面接管状态
- 模块目录与领域边界重构
- 审计与日志体系规范化
- 通用适配层与外部系统映射机制

### 低优先级

- logrus -> slog
- 更换 UI 框架
- 过早拆服务
- 过早引入复杂消息系统

## 九、最终结论

如果这个 fork 项目的未来方向是“做自己的运维平台”，而不是“持续低成本吸收 upstream 代码”，那么推荐路线是：

- 保留：`Go + Gin + Vue 3 + Element Plus`
- 升级：`Vite + TypeScript + Pinia + golang-jwt/jwt`
- 重构：`PostgreSQL + migration + asynq`
- 重心：先做模块边界，再做技术替换

一句话总结：

**这不是一次简单的技术升级，而是一次从“原项目二开”走向“独立平台演进”的架构转向。**

补充一句：

**这个平台未来应优先做成“可替换外部依赖的通用底座”，而不是与任何单一外部工具深度绑定的垂直定制系统。**
