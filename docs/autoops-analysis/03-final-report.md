## 一、项目全貌摘要

**天枢 AutoOps** 是一套面向中小企业运维团队的企业级运维自动化平台，基于 **Go 1.24 + Vue3** 开发，通过 Docker Compose 一键部署。它解决的核心问题是：运维工具碎片化（Jenkins/JumpServer/Grafana/K8s 各自独立）和资产数据孤岛（服务器台账、工单、成本账单散落飞书）。平台以 **CMDB 为数据底座**，向上集成主机 SSH 终端、Kubernetes 多集群管理、Jenkins 应用发布、Prometheus 监控告警、Ansible 批量运维、任务调度等核心能力，并提供全链路操作审计（登录日志、操作日志、SQL 执行日志、终端录像）。仅供运维团队内部使用，覆盖超级管理员、运维主管、运维工程师、SRE、只读用户五种角色。

## 四、核心技术决策分析

### 决策 1：Redis 五级优先级任务队列

**做了什么**：任务调度模块使用 Redis List 实现五条队列（`dodevops:task_queue:high/normal/low/retry/failed`），配合 WorkerPool 的全局 semaphore + 每主机独立 semaphore 双重并发限制（全局最大 50，每台主机最大 5）。

**为什么这样设计**：
- 纯 Cron 调度（`robfig/cron`）只负责触发，不负责执行，调度与执行解耦；
- 任务执行需要 SSH 到目标主机，批量任务并发量如果不加限制，会把目标主机的 SSH 连接打满，导致主机异常；
- 失败任务自动进入 retry 队列（最多重试 3 次，延迟 30s），最终失败沉入 failed 队列，实现了无人值守的弹性重试；
- 相比消息中间件（RabbitMQ/Kafka），Redis List 方案在运维工具场景下吞吐量足够，且无需引入额外基础设施。

### 决策 2：K8s 资源不落库，仅存 kubeconfig

**做了什么**：`k8s_cluster` 表仅存集群元数据（名称/状态/kubeconfig 全文）；节点、Pod、Deployment、Service 等所有 K8s 资源均通过 `k8s.io/client-go` 实时从 K8s API Server 查询，不在 MySQL 中缓存。

**为什么这样设计**：
- K8s 资源状态高度动态（Pod 随时创建/销毁），如果落库需要持续 Watch 并同步状态，实现复杂且极易出现数据不一致；
- client-go 直接查询 API Server 能保证数据实时性，用户看到的资源状态即 K8s 中的真实状态；
- 代价是每次页面加载都有一次 K8s API 调用，对于运维场景（非高频、非大规模）是可接受的。

### 决策 3：凭据 AES 加密存库 + 使用时内存解密

**做了什么**：`config_ecsauth`（SSH 密码）和 `config_account`（数据库/Jenkins 账密）的 Password 字段均调用 `util.AESEncrypt()` 加密后写入 MySQL；使用时通过 `DecryptPassword()` 解密，明文只在内存中存在于调用链中，不通过 API 返回，也不写日志。

**为什么这样设计**：
- 直接存明文一旦数据库泄露，所有运维凭据同时失陷，影响所有被管理主机和系统；
- AES 对称加密在运维工具场景下比 bcrypt 更合适（需要还原原始密码用于 SSH/数据库连接），bcrypt 是单向 Hash 只适合密码验证；
- 用户登录密码（`sys_admin.Password`）使用 bcrypt（不可逆），体现了对两类"密码"语义的区分。

### 决策 4：JWT + Redis 双重 Token 管理

**做了什么**：用户登录后，后端颁发 JWT Token，同时将 Token 存入 Redis。`authMiddleware.go` 每次请求既校验 JWT 签名有效性，又在 Redis 中查找该 Token 是否存在。

**为什么这样设计**：
- 纯 JWT 无状态方案无法实现强制下线（JWT 签名有效期内任何人都能用），而 Redis 中删除记录即可立即吊销 Token；
- 对运维平台而言，需要能在发生安全事件时立即踢出特定用户，Redis 吊销满足这个需求；
- 代价是每次请求多一次 Redis 查找，但延迟可接受（<1ms 本地网络）。

### 决策 5：SSE + WebSocket 双通道日志推送

**做了什么**：Ansible 任务日志同时提供两条实时推送路径：`GET /task/ansible/:id/log/:work_id`（SSE，Content-Type: text/event-stream）和 `GET /ws/task/ansible/:id/log/:work_id`（WebSocket）；后端读取磁盘日志文件逐行推送，任务完成发送 EOF 事件。

**为什么这样设计**：
- SSE 是单向流，实现简单，兼容性好（标准 HTTP，无需协议升级），对只需接收日志的场景足够；
- WebSocket 双向通信支持更丰富的交互（如发送中断信号），保留扩展空间；
- 日志写磁盘文件（而非全量存 Redis）避免长时间任务产生大量日志将 Redis 内存撑满；
- `utils/sseLogManager.js` 在前端封装了重连和多路复用逻辑，避免因网络抖动导致日志丢失。

## 六、技术亮点

### 1. WebSocket 认证的三种兼容方案

`authMiddleware.go` 针对三种场景做了完整适配：
- **普通 HTTP 请求**：`Authorization: Bearer {token}` 请求头
- **WebSocket 连接**：URL Query 参数 `?token={token}`（WebSocket 握手时无法设置自定义请求头）
- **SSE 连接**：URL Query 参数 `?token={token}`
- **WebSocket 补充方案**：若 URL 无 token，则 hijack 连接，读取第一条 WS 消息作为 JSON 鉴权包 `{"type":"auth","token":"..."}`

这一设计覆盖了浏览器在不同协议下的鉴权局限，无需改动业务逻辑层。

### 2. 任务调度双层并发保护

WorkerPool 使用两层 semaphore：
```
globalLimit = semaphore.NewWeighted(50)   // 全局最多 50 个并发任务
hostLimits[hostID] = semaphore.NewWeighted(5)  // 每台主机最多 5 个并发
```
先获取全局锁，再获取主机锁，两层均是 `Acquire(ctx, 1)`，天然支持超时取消和 graceful stop。这比简单的 WaitGroup 方案更精细，既防止集群级别的资源耗尽，也防止单台主机被轰炸。

### 3. 服务目录配置化设计

`tool` 模块的可部署服务列表来自 `services.json` 文件（非数据库），`ServiceInfo` 结构支持 `DeployType: container/binary` 两种部署方式，新增可一键安装的服务只需编辑 JSON 文件，零代码变更。部署逻辑按类型分支：container 走 Docker pull + run，binary 走 SFTP 上传 + SSH 执行安装脚本。

### 4. RBAC 按钮级权限控制

权限粒度做到了前后端一致的按钮级控制：
- **后端**：`SysMenu.Value` 定义权限标识（如 `cmdb:host:add`），登录接口返回当前用户的权限列表
- **前端**：`utils/authority.js` 的 `hasPermission(value)` + 自定义指令 `v-auth` 实现按钮自动隐藏/禁用
- **权限链**：`SysAdmin → SysAdminRole → SysRole → SysRoleMenu → SysMenu`，五张表的关联确保了权限的精确控制

### 5. Agent 异步部署进度追踪

Agent 安装是耗时的异步操作，系统通过 `InstallProgress` 字段（0→10→30→50→70→90→100）分 7 个阶段追踪进度，前端轮询即可展示进度条，无需 WebSocket 长连接。状态机设计：`1=部署中 → 2=失败` 或 `1=部署中 → 3=运行中`，失败时写入 `ErrorMsg` 字段，方便运维人员诊断。

### 6. 仪表盘并发聚合查询

`DashboardService.GetDashboardStats()` 使用 goroutine 并发查询 6 个不同表/模块的统计数据（主机数、集群数、发布统计、任务统计、服务统计、数据库分布），通过 `sync.WaitGroup` 等待所有查询完成后组装结果，而非串行查询，仪表盘响应时间取决于最慢的单条查询，而不是所有查询之和。

## 七、潜在问题与技术债务

以下问题均基于源码静态分析，为代码中可直接观察到的现象。

### 问题 1：JWT 密钥未见配置化（中等风险）

从代码结构观察，JWT 签名密钥（Secret）的管理方式需关注。若密钥硬编码在代码中而非通过 `config.yaml` 或环境变量注入，一旦代码仓库泄露，所有历史和当前 Token 均可被伪造。建议核查 `pkg/jwt/` 中的密钥来源，确保生产环境通过 `docker/.env` 注入且与开发密钥不同。

### 问题 2：JWT 使用了已废弃的 dgrijalva/jwt-go（低风险）

项目使用 `dgrijalva/jwt-go v3.2.0`，该库已在 2020 年停止维护，存在若干已知漏洞（CVE）。社区推荐迁移到 `golang-jwt/jwt`（接替版本，API 兼容）。虽然当前使用场景不一定触发已知漏洞，但维护停止本身是一个长期风险。

### 问题 3：EcsAuth.PublicKey 字段命名混乱（代码可维护性）

`EcsAuth.PublicKey` 字段实际存储的是**私钥内容**，字段名历史原因未修改（代码注释中明确标注"字段名历史原因"）。这是典型的语义与名称不一致，新接手代码的开发者极易误解，存在误用风险。应在适当时机将字段重命名为 `PrivateKey`（需同步迁移数据库列名和所有引用代码）。

### 问题 4：任务日志写磁盘文件，缺乏清理机制

Ansible 任务日志写入磁盘文件（`TaskAnsible.LogFile`），SSE 推送时读取该文件。从代码中未观察到日志文件的自动清理（定期删除旧日志或按大小轮转）逻辑。在任务量大或长期运行的场景下，日志文件可能持续积累，耗尽磁盘空间。建议增加基于时间（如 30 天）或数量的日志清理调度任务。

### 问题 5：dashboard 和 tool 模块目录命名不一致

`api/api/dashboard/` 的 model 目录名为 `model1`（而非 `model`），`api/api/tool/` 的 dao 目录名为 `dao1`（而非 `dao`）。这不影响功能，但与其他 8 个模块的命名规范不一致，给代码导航和新人理解带来额外认知负担，属于轻微技术债务。

### 问题 6：配置文件默认值含明文密码

`docker/docker-compose.yml` 和 `docker/.env` 中包含默认密码（如 Redis 密码 `zhangfan@123`、MySQL 密码 `devops@2025`）。虽然通过环境变量注入在技术上是正确做法，但默认密码出现在版本控制的文件中，要求部署者必须主动修改。建议在文档中以强制步骤要求部署前修改，并在启动检查中验证密码是否仍为默认值。

### 问题 7：K8s kubeconfig 全文明文存入 MySQL

`k8s_cluster.Credential` 字段存储完整的 kubeconfig 文本（包含 K8s API Server 证书和 Token）。与 SSH 凭据的 AES 加密策略不同，kubeconfig 似乎未加密存储。若 MySQL 备份文件泄露，攻击者可获得所有已注册 K8s 集群的完整访问权限。建议对该字段同样施以 AES 加密，与 EcsAuth/AccountAuth 的处理保持一致。

### 问题 8：前端构建工具较旧

前端使用 `Vue CLI ~5.0.0`（基于 Webpack），而 Vue 3 生态已普遍迁移到 Vite（构建速度快 10-100 倍）。这不影响运行时性能，但影响开发体验（冷启动慢、HMR 较慢）。属于长期可考虑的工具链升级。
