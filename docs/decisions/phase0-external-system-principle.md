# 阶段0决策：外部系统接入原则

> 决策时间：2026-04-23
> 决策状态：已确认
> 相关文档：`docs/roadmap.md`

---

## 背景

AutoOps 需要接入多个外部系统：

- 域名管理（dnsmgr）
- 运营工单（飞书多维表格）
- 站点管理（飞书多维表格）
- Jenkins（CI/CD）
- Prometheus（监控）
- 云厂商 SDK（资源同步）
- SSH/SFTP（主机管理）
- 通知渠道（飞书、钉钉等）

核心问题是：**这些外部系统应该如何接入，才能保证未来可以替换？**

---

## 决策

**所有外部系统都视为可替换依赖，不绑定到核心模型里。**

具体约束：

1. 核心域不直接依赖任何具体外部产品
2. 外部平台统一通过 adapter/provider 方式接入
3. 平台内部数据模型只保存通用业务字段、外部对象映射关系、同步状态和审计信息
4. 不把任何第三方系统的专有字段直接铺满核心业务主表
5. 替换外部系统时，目标是主要调整适配层，而不是推翻页面、业务服务和数据库主结构

---

## 理由

### 为什么需要这个原则

**教训来源**：

1. **外部系统会变**
   - 飞书可能换成其他协同工具
   - dnsmgr 可能换成其他 DNS 管理平台
   - 云厂商可能从 AWS 换成阿里云
   - 如果外部系统的字段直接进了核心表，替换时要改数据库结构

2. **外部系统的 API 会变**
   - 第三方 API 随时可能升级或废弃
   - 如果调用代码散落在业务逻辑里，改起来很痛苦

3. **不同环境用不同外部系统**
   - 开发环境可能用 mock
   - 测试环境可能用另一套
   - 如果耦合太深，测试很难做

---

## 架构模式

### 三层结构

```text
核心域（Core Domain）
  ↑ 依赖
业务能力域（Business Domain）
  ↑ 依赖
集成适配层（Integration Layer）
  ↕ 对接
外部系统（External Systems）
```

### 集成适配层的职责

每个外部系统接入应包含：

1. **Provider 接口**：定义平台需要的能力（不依赖具体实现）
2. **Adapter 实现**：实现 Provider 接口，调用具体外部系统
3. **同步任务**：定期从外部系统拉取数据，写入平台内部模型
4. **回写服务**：把平台内的变更推送到外部系统

### 数据模型原则

**核心业务表只存通用字段**：

```sql
-- 好的做法：通用字段 + 外部映射
CREATE TABLE domain_records (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,        -- 通用字段
    type VARCHAR(10) NOT NULL,         -- 通用字段
    value TEXT NOT NULL,               -- 通用字段
    external_source VARCHAR(50),       -- 来自哪个外部系统
    external_id VARCHAR(255),          -- 外部系统的 ID
    sync_status VARCHAR(20),           -- 同步状态
    last_synced_at TIMESTAMP,          -- 最后同步时间
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);

-- 不好的做法：把 dnsmgr 专有字段直接放进来
-- dnsmgr_record_id, dnsmgr_zone_id, dnsmgr_ttl_type ...
```

## 当前接入计划

### 首批接入（阶段2）

| 外部系统 | 接入方式 | 核心能力 |
|---|---|---|
| 飞书多维表格 | HTTP API | 运营工单同步、站点管理同步 |
| dnsmgr | HTTP API | 域名记录查询和管理 |

### 后续接入（阶段3+）

| 外部系统 | 接入方式 | 核心能力 |
|---|---|---|
| Jenkins | HTTP API | CI/CD 触发和状态同步 |
| Prometheus | HTTP API | 告警规则和指标查询 |
| 云厂商 SDK | SDK | 资源同步 |

---

## 接入层骨架（阶段1已落地）

`/api/v1/integration/catalog` 接口已提供外部系统目录，返回当前配置的外部系统清单。

这是接入层的入口，后续每个外部系统的 adapter 都在这个框架下扩展。

---

## 约束条件

这个原则基于以下约束：

1. **外部系统不稳定**：第三方工具随时可能变化
2. **多环境需求**：开发/测试/生产可能用不同的外部系统
3. **替换成本**：如果耦合太深，替换外部系统的成本会很高

如果约束条件变化（比如某个外部系统已经确定长期不会换），可以适当放宽这个原则，但要在对应模块的文档里说明。

---

## 后续行动

1. 阶段2第一个接入模块（运营工单或站点管理）需要实现最小 Provider 接口
2. 用第一个真实接入验证这个原则是否可行
3. 根据验证结果调整接口设计，不要提前过度设计
